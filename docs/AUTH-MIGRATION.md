# แผนการ migrate รหัสผ่านโรงเรียนจาก plaintext (legacy) → hash

## ปัญหาเดิม

บัญชีโรงเรียน ~30,805 แห่งอยู่ในตาราง legacy `` `user` `` ของระบบ SSRA เดิม โดย **รหัสผ่านเก็บเป็น plaintext**
(5–6 ตัวอักษร) การเข้าสู่ระบบเดิมเทียบรหัสผ่านตรง ๆ (`password === legacy.password`) ซึ่ง:

- เสี่ยงต่อการรั่วไหลถ้าฐานข้อมูลถูกเข้าถึง (ไม่มีการแฮช)
- ตาราง `` `user` `` เป็น **read-only** สำหรับแอปนี้ (มีระบบเดิมอื่นใช้ร่วม) — แก้รหัสในตารางนั้นไม่ได้

## กลยุทธ์ที่เลือก: Lazy migration (migrate ตอน login สำเร็จ)

แทนที่จะ batch-migrate ทั้ง 30,805 แถว (ซึ่งต้องรู้ plaintext ทุกบัญชีอยู่แล้ว และเขียนลง read-only table ไม่ได้)
เราย้ายทีละบัญชี **เฉพาะตอนเจ้าของ login สำเร็จ** เพราะนั่นคือจังหวะเดียวที่เรามี plaintext ที่ถูกต้องในมือ:

1. ผู้ใช้กรอกรหัส 8 หลัก + รหัสผ่าน
2. ลำดับการตรวจใน `resolveLogin` ([app/api/auth/login/route.ts](../app/api/auth/login/route.ts)):
   - **(1)** ค้นตาราง `users` (บัญชี local, แฮชแล้ว) ก่อน
   - **(2)** ถ้าไม่พบ → ค้นตาราง legacy `` `user` `` เทียบ plaintext
3. เมื่อ **legacy match สำเร็จ** → สร้างแถวใหม่ในตาราง `users` ที่เราเป็นเจ้าของ ด้วย:
   - `username` = รหัส 8 หลักเดิม
   - `password_hash` = `scrypt(รหัสที่เพิ่งกรอก)` (ผ่าน `createUser`)
   - `role = "school"`, `school_code` = รหัส 8 หลัก (คีย์จำกัดขอบเขตข้อมูลเดิม)
4. ครั้งถัดไปที่ login → ขั้น (1) เจอบัญชี local แล้ว → ตรวจด้วย **hash** ไม่แตะ plaintext อีก

ผลลัพธ์: ไม่มี downtime, ไม่ต้อง batch job, ตาราง legacy ไม่ถูกเขียน, ผู้ใช้ไม่รู้สึกถึงความเปลี่ยนแปลง
(username/password เดิม) และรหัสผ่านทยอยกลายเป็น hash ตามการใช้งานจริง

## การกันโรงเรียนถูกล็อกออก (self-healing rehash)

จุดเสี่ยงเดียวของ lazy migration: หลัง migrate แล้ว ถ้ารหัสผ่านในตาราง legacy ถูกเปลี่ยน (จากระบบเดิมอื่น)
บัญชี local ที่แฮชไว้จะยังเป็นรหัสเก่า → ขั้น (1) จะ fail และไม่ยอมตกไป legacy → โรงเรียนเข้าไม่ได้

แก้โดย: ในขั้น (1) **เฉพาะบัญชีบทบาท `school`** ถ้ารหัสไม่ตรง ให้ลองเทียบกับ legacy อีกครั้ง —
ถ้า legacy ตรง (แปลว่ารหัสถูกเปลี่ยน) ให้ **rehash ทับ** (`updateUser(id, { password })`) แล้วให้ผ่าน
บัญชี `admin`/`ssra_admin` จะ **ไม่** ตกไป legacy เด็ดขาด (กัน legacy row มา bypass บัญชีผู้ดูแล)

## ผลข้างเคียงที่ยอมรับ

- บัญชีโรงเรียนที่ migrate แล้วจะ **ปรากฏในหน้า "จัดการผู้ใช้"** (เดิมจัดการเฉพาะ local) — ถือเป็นข้อดี
  (admin รีเซ็ตรหัส/ระงับบัญชีโรงเรียนได้) ปริมาณแถวใน `users` จะโตตามจำนวนโรงเรียนที่เข้าใช้จริง
- ถ้า `createUser` ล้ม (เช่น race กับอีก request, หรือ DB ชั่วคราวมีปัญหา) → ยังให้เข้าระบบด้วย session
  แบบ legacy ได้ตามเดิม แล้วค่อย migrate รอบถัดไป (best-effort ไม่ทำให้ login ล้ม)

## Phase 1 — Batch backfill (พร้อมใช้แล้ว)

`scripts/migrate-legacy-users.mjs` (สั่งด้วย `npm run users:migrate`) ทำ backfill ล่วงหน้า: อ่านทุกบัญชีใน
ตาราง legacy `` `user` `` ที่ยัง **ไม่มี** ใน `users` แล้วสร้างแถว `users` (role `school`, `school_code` = รหัส
8 หลัก) โดยแฮชรหัส plaintext ด้วย scrypt (รูปแบบตรงกับ `lib/auth.ts#hashPassword` เป๊ะ) — เพื่อให้ทุก
บัญชีเข้าสู่ระบบผ่าน **hashed path** ทันที ไม่ต้องรอ lazy migration และเลิกเทียบ plaintext ตอน login

- **DEFAULT = DRY-RUN** (ไม่เขียนอะไร) — ต้องใส่ `--commit` จึงเขียนจริง; `--limit N` ทำเป็นชุด
- **idempotent + resumable:** ข้ามบัญชีที่มีใน `users` แล้ว (LEFT JOIN … IS NULL) → รันซ้ำ/ทำต่อได้
- ตาราง legacy ยังถูก **อ่านอย่างเดียว** — สคริปต์เขียนลง `users` เท่านั้น
- ⚠️ scrypt ต่อบัญชี ~50–100 ms → ~30k บัญชีใช้เวลาราว 30–50 นาที (แบ่ง `--limit` ได้)
- ผลข้างเคียงที่ต้องรู้: `users` จะมี scrypt-hash ของรหัสที่ **ยังสั้น/อ่อน** (5–6 ตัว) — ดีกว่า plaintext
  แต่ยัง brute-force ได้ถ้า `users` รั่ว → จึงต้องมี Phase 2 ต่อ

## Phase 2 — บังคับตั้งรหัสใหม่ที่แข็งแรง (ยังไม่ทำ — ต้องตัดสินใจ UX)

- **Forced password reset ตอน login ครั้งแรก:** ต้องเพิ่มคอลัมน์ `must_change_password`, route เปลี่ยนรหัส,
  หน้า UI + ช่องทางกู้บัญชี (โรงเรียนจำนวนมาก) — เป็นงาน feature เต็มที่ควร scope แยก
- **ปิดช่องทาง legacy:** เมื่อสัดส่วน migrate สูงพอ เพิ่ม flag ปิดขั้น (2) ใน `resolveLogin` บางสภาพแวดล้อม
- **นโยบายความยาวรหัสผ่าน:** บังคับรหัสใหม่ ≥ เกณฑ์ที่กำหนดตอน reset
