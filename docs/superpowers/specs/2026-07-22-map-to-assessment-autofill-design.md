# Map-to-Assessment Autofill Design

**วันที่:** 22 กรกฎาคม 2569

**สถานะ:** รออนุมัติสเปกก่อนจัดทำแผนพัฒนา

**ขอบเขต:** ส่งผลวิเคราะห์จากแผนที่ 3 มิติ (Cesium) ไปสร้างหรือปรับปรุงแบบประเมินของโรงเรียน

## 1. เป้าหมาย

เพิ่มปุ่มบนหน้า `/map` เพื่อบันทึกข้อมูลประกอบเกณฑ์จากการวิเคราะห์ GIS และเปิดแบบประเมินที่เกี่ยวข้อง โดยระบบต้อง:

- มีแบบประเมินได้โรงเรียนละ 1 ฉบับต่อปี พ.ศ.
- ปรับปรุงแบบร่างของปีปัจจุบัน หากมีอยู่แล้ว
- สร้างแบบร่างใหม่และกรอกข้อมูลที่หาได้อัตโนมัติ หากยังไม่มีแบบประเมินของปีปัจจุบัน
- ไม่แก้ไขแบบประเมินที่ส่งแล้ว และเปิดให้ดูฉบับเดิมแทน
- บันทึกผล GIS เป็นข้อมูลประกอบการพิจารณาแบบอ่านอย่างเดียว
- นำผล GIS ไปกรอกค่าที่มีผลต่อคะแนนในมิติที่ 3 โดยผู้ประเมินยังตรวจทานและแก้ไขได้ก่อนส่ง

## 2. ข้อกำหนดและขอบเขตข้อมูล

### 2.1 ปีและเจ้าของแบบประเมิน

- ใช้รหัสโรงเรียนจาก session เท่านั้น ไม่รับรหัสโรงเรียนจาก request body
- ปีการประเมินคือปี พ.ศ. ปัจจุบัน คำนวณจากเวลา `Asia/Bangkok` (`ปี ค.ศ. + 543`)
- บังคับความเป็นหนึ่งเดียวด้วยข้อกำหนดเฉพาะ `(owner_school_code, assessment_year)`
- ก่อนเพิ่ม unique index ต้องตรวจสอบและรายงานข้อมูลซ้ำเดิม เพื่อไม่รวม ลบ หรือเลือกฉบับแทนผู้ใช้โดยอัตโนมัติ

### 2.2 สถานะของแบบประเมิน

| สถานะปัจจุบัน | การทำงาน |
|---|---|
| ไม่มีแบบประเมินในปีปัจจุบัน | สร้างแบบร่าง กรอกข้อมูลโรงเรียนที่มี และบันทึก GIS |
| มีแบบร่าง | ปรับปรุงแบบร่างฉบับเดิมและบันทึก GIS ล่าสุด |
| ส่งแล้ว | ไม่เปลี่ยนข้อมูล ส่งผลลัพธ์ว่าแบบถูกล็อก และคืน ID สำหรับเปิดดู |

สถานะอื่นที่มีความหมายเทียบเท่าแบบร่างให้แก้ไขได้เฉพาะเมื่อกฎสถานะเดิมของระบบอนุญาต ส่วนสถานะที่มีความหมายว่าส่งหรือรับรองแล้วต้องถือว่าถูกล็อก

## 3. แนวทางสถาปัตยกรรม

ใช้ API เดียวแบบ atomic:

`POST /api/assessments/from-map`

เหตุผลคือการสร้างแบบประเมินและการบันทึก GIS ต้องสำเร็จหรือยกเลิกพร้อมกัน ป้องกันการเหลือแบบประเมินว่างเมื่อขั้นตอนวิเคราะห์หรือบันทึกข้อมูลล้มเหลว

### 3.1 ลำดับการทำงาน

1. ตรวจสอบ session และอ่านรหัสโรงเรียนจาก session
2. คำนวณปี พ.ศ. ปัจจุบันตามเวลา `Asia/Bangkok`
3. ตรวจสอบ payload และคำนวณ/ตรวจสอบผล GIS ซ้ำฝั่ง server ตามกฎเดียวกับ API GIS เดิม
4. เปิด database transaction
5. ค้นหาแบบประเมินของโรงเรียนและปีปัจจุบัน โดยล็อกแถวหรือใช้กลไกที่ป้องกันคำขอพร้อมกัน
6. หากส่งแล้ว ให้ยกเลิกการเปลี่ยนแปลงและตอบสถานะ `locked` พร้อม assessment ID
7. หากมีแบบร่าง ให้ปรับปรุงฉบับเดิม
8. หากไม่มี ให้สร้างแบบร่างและกรอกข้อมูลหลักของโรงเรียนเท่าที่มีจริง
9. บันทึกข้อมูลประกอบ GIS และกรอกคำตอบมิติที่ 3 ที่อนุมานได้
10. commit transaction และตอบ assessment ID กับผลลัพธ์ `created` หรือ `updated`
11. หน้าแผนที่นำผู้ใช้ไปที่ `/assessment/{id}`

หากเกิด unique-key conflict จากคำขอพร้อมกัน ให้ API อ่านฉบับที่มีอยู่ใหม่ภายในแนวทางที่ปลอดภัย แล้วปรับปรุงฉบับนั้นได้เฉพาะเมื่อยังเป็นแบบร่าง ห้ามสร้างฉบับที่สอง

## 4. แบบจำลองข้อมูล GIS

ขยาย `GisAnalysis` เดิมเพื่อหลีกเลี่ยงการเก็บข้อมูลชุดเดียวกันซ้ำซ้อน โดยแยกค่าที่มีความหมายต่างกันอย่างชัดเจน

### 4.1 ระดับความสูงและภูมิประเทศ

- ระดับความสูง ณ หมุดที่ตั้งโรงเรียนแบบจุด (`schoolMarkerElevationM`)
- ระดับความสูงเฉลี่ย ต่ำสุด และสูงสุดของพื้นที่วิเคราะห์
- ความต่างระดับ (`reliefM`)
- ความลาดชันเฉลี่ยและสูงสุด
- ชั้นความลาดชันตามเกณฑ์ที่ระบบใช้อยู่
- ระดับความสูงสูงสุดในรัศมี 1 กิโลเมตรจากที่ตั้ง

ห้ามนำระดับความสูงเฉลี่ยของพื้นที่มาใช้แทนระดับความสูง ณ หมุดโรงเรียน

### 4.2 เส้นทางจากศาลากลางจังหวัดถึงโรงเรียน

- ระยะทางและเวลาเดินทาง
- อัตราความคดเคี้ยว ความเร็วอ้างอิง และ elevation gain
- ระดับความสูงสูงสุดตลอดเส้นทาง
- พิกัดละติจูด/ลองจิจูดของจุดสูงสุดตลอดเส้นทาง
- ระดับความสูงสูงสุดในช่วง 5 กิโลเมตรสุดท้าย

ธงแดง “จุดสูงสุดบนเส้นทาง” ต้องอ่านค่าพิกัดและระดับความสูงจากข้อมูลเดียวกับที่บันทึกในแบบประเมิน ส่วนธงโรงเรียนต้องใช้ `schoolMarkerElevationM`

### 4.3 อาคาร ประชากร และขอบเขตพื้นที่

- จำนวนอาคารและประมาณการประชากรในรัศมี 500, 1,000 และ 1,500 เมตร
- ผลสรุปพื้นที่ polygon เมื่อผู้ใช้วาดขอบเขตครบถ้วน
- พื้นที่ polygon และค่าสรุปที่ระบบคำนวณได้ตามแบบจำลองเดิม

### 4.4 การจัดประเภทและที่มาข้อมูล

- ประเภทภูมิประเทศ/ชุมชนที่วิเคราะห์ได้
- คะแนน GIS อัตโนมัติที่เกี่ยวข้องกับมิติที่ 3
- แหล่งข้อมูลและรุ่น/วิธีวิเคราะห์เท่าที่ระบบทราบ
- วันเวลาที่วิเคราะห์ โดยบันทึกในรูปแบบเวลามาตรฐานและแสดงผลตาม `Asia/Bangkok`

ค่าที่ไม่มีแหล่งข้อมูลจริงต้องเป็นค่าว่าง ไม่สร้างข้อมูลสมมติ โดยเฉพาะจำนวนนักเรียนและสำนักงานเขตพื้นที่การศึกษา ซึ่งแหล่งข้อมูลหลักปัจจุบันยังไม่รับประกันว่ามีค่าเหล่านี้

## 5. การกรอกแบบประเมิน

### 5.1 ส่วนข้อมูลประกอบเกณฑ์

เพิ่มส่วนอ่านอย่างเดียวชื่อ **“ข้อมูลประกอบเกณฑ์จากแผนที่ 3 มิติ”** ในหน้าแบบประเมิน แสดงข้อมูลสำคัญจากหัวข้อ 4 พร้อมแหล่งข้อมูลและเวลาวิเคราะห์

ข้อมูลส่วนนี้แก้ไขด้วยมือจากหน้าแบบประเมินไม่ได้ การเปลี่ยนแปลงต้องมาจากการวิเคราะห์และบันทึกบนหน้าแผนที่ในขณะที่แบบยังเป็นแบบร่าง

### 5.2 คำตอบที่มีผลต่อคะแนน

- ระบบแปลงผล GIS เป็นคำตอบมิติที่ 3 ด้วยกฎคะแนนที่มีอยู่
- คำตอบที่กรอกอัตโนมัติยังแก้ไขได้ก่อนส่งแบบประเมิน
- การแก้คำตอบมิติที่ 3 ไม่ย้อนกลับไปแก้ข้อมูลประกอบ GIS
- ต้องแสดงให้ผู้ใช้ทราบว่าค่าใดมาจากการวิเคราะห์อัตโนมัติ

### 5.3 ข้อมูลโรงเรียนเมื่อสร้างฉบับใหม่

กรอกเฉพาะข้อมูลที่อ่านได้จาก session และ master data ที่มีอยู่จริง เช่น รหัสโรงเรียน ชื่อโรงเรียน จังหวัด และพิกัด ห้ามเดาค่าของฟิลด์ที่ไม่มีแหล่งข้อมูล

## 6. ประสบการณ์ผู้ใช้บนหน้าแผนที่

เพิ่มปุ่มหลัก:

**“บันทึกข้อมูลประกอบเกณฑ์และกรอกแบบประเมิน”**

ปุ่มทำงานได้เมื่อข้อมูลขั้นต่ำสำหรับวิเคราะห์ครบ หากข้อมูลไม่ครบให้แจ้งรายการที่ขาด และไม่สร้างหรือแก้ไขแบบประเมินบางส่วน

ผลลัพธ์ที่แสดง:

- `created`: สร้างแบบประเมินปีปัจจุบันและกรอกข้อมูลแล้ว
- `updated`: ปรับปรุงแบบร่างปีปัจจุบันแล้ว
- `locked`: แบบประเมินปีปัจจุบันส่งแล้ว จึงเปิดดูได้อย่างเดียว

หลังสำเร็จให้นำไปหน้าแบบประเมินเดียวกันตาม ID ที่ API คืนมา และป้องกันการกดซ้ำระหว่างกำลังส่งคำขอ

## 7. ความปลอดภัย ความถูกต้อง และข้อผิดพลาด

- ตรวจสิทธิ์การเข้าถึง assessment ทุกครั้งตามกฎเดิมของระบบ
- ไม่ยอมรับ school code, assessment ID, คะแนนสำเร็จรูป หรือสถานะจาก client เพื่อใช้ตัดสินเจ้าของ/สิทธิ์
- ตรวจรูปแบบและขอบเขตของพิกัด ระยะทาง ระดับความสูง และชุดข้อมูล polygon
- server คำนวณค่าที่มีผลต่อคะแนนซ้ำหรือสร้างจากอินพุตดิบที่ตรวจสอบแล้ว
- ใช้ transaction ครอบคลุมการสร้าง/แก้ไข assessment, GIS และคำตอบอัตโนมัติ
- แบบที่ส่งแล้วต้องไม่เปลี่ยน แม้ client ส่งคำขอเก่าหรือแก้ payload
- ตอบ error ที่แยกได้ระหว่างไม่ได้รับอนุญาต ข้อมูลไม่ครบ การวิเคราะห์ล้มเหลว แบบถูกล็อก และข้อขัดแย้งของข้อมูล
- ไม่เปลี่ยนลำดับหรือเลือก assessment ด้วยแนวทาง “draft ก่อน submitted” โดยไม่กรองปี ต้องค้นหาด้วยโรงเรียนและปีปัจจุบันโดยตรง

## 8. การย้ายข้อมูล

1. เพิ่มฟิลด์ GIS แบบ backward-compatible ใน JSON state โดยฟิลด์ใหม่เป็น optional สำหรับแบบเก่า
2. ตรวจสอบ assessment ที่มี `(owner_school_code, assessment_year)` ซ้ำ
3. หากพบข้อมูลซ้ำ ให้ migration หยุดพร้อมรายงานรายการที่ต้องตัดสินใจ ห้ามลบหรือรวมอัตโนมัติ
4. เมื่อข้อมูลสะอาดจึงเพิ่ม composite unique index
5. หน้าแสดงผลต้องรองรับ assessment เก่าที่ยังไม่มีฟิลด์ GIS ใหม่ โดยแสดง “ไม่มีข้อมูล” แทนการคำนวณค่าทดแทน

## 9. การทดสอบและเกณฑ์ยอมรับ

### 9.1 Automated tests

- ไม่มีแบบปีปัจจุบัน: สร้างแบบร่างหนึ่งฉบับและกรอกข้อมูลที่มี
- มีแบบร่าง: ปรับปรุง ID เดิมและไม่เพิ่มจำนวนฉบับ
- มีแบบส่งแล้ว: ไม่เปลี่ยน state และคืน `locked` พร้อม ID เดิม
- ปีที่ใช้ตรงกับปี พ.ศ. ปัจจุบันใน `Asia/Bangkok` รวมกรณีรอยต่อวัน/ปี
- session school code มีอำนาจเหนือค่าปลอมที่ client ส่งมา
- คำขอพร้อมกันไม่สร้างข้อมูลซ้ำ
- transaction rollback ครบเมื่อการบันทึก GIS หรือการกรอกคำตอบล้มเหลว
- `schoolMarkerElevationM` ไม่ปะปนกับค่าเฉลี่ยพื้นที่
- ธงจุดสูงสุด พิกัด และค่าที่บันทึกใช้ route profile ชุดเดียวกัน
- กฎแปลง GIS เป็นคำตอบมิติที่ 3 ให้ผลตรงตามเกณฑ์เดิม
- แบบเก่าไม่มีฟิลด์ใหม่แล้วยังเปิดได้
- migration ตรวจพบข้อมูลซ้ำก่อนเพิ่ม unique index

### 9.2 การตรวจสอบระบบจริง

- รัน unit/integration test ทั้งชุดและ production build
- ทดสอบผ่าน browser ตั้งแต่ `/map` วิเคราะห์ข้อมูล กดปุ่ม ไปจนถึง `/assessment/{id}`
- เปรียบเทียบระดับความสูงบนธงโรงเรียน ธงจุดสูงสุด และข้อมูลในแบบประเมินให้ตรงกัน
- ทดสอบทั้งสามสถานะ `created`, `updated`, `locked`
- รีเฟรชหน้าและเข้าสู่ระบบใหม่เพื่อยืนยันว่าข้อมูลคงอยู่และสิทธิ์ยังถูกต้อง

## 10. สิ่งที่ไม่อยู่ในขอบเขต

- การสร้าง master data ใหม่เพื่อเติมจำนวนนักเรียนหรือสำนักงานเขตพื้นที่
- การแก้ไขแบบประเมินที่ส่งแล้ว
- การสร้างตาราง GIS แยกใหม่ หาก JSON state เดิมยังรองรับการขยายได้
- การเปลี่ยนกฎคะแนนนอกเหนือจากการนำกฎมิติที่ 3 เดิมมาใช้กับข้อมูล GIS
- การรวมแบบประเมินซ้ำเดิมโดยอัตโนมัติ

## 11. ผลลัพธ์ที่ต้องส่งมอบในขั้นพัฒนา

- schema/type สำหรับข้อมูล GIS ที่ขยายแล้ว
- migration และตัวตรวจข้อมูลซ้ำก่อน unique index
- atomic API `POST /api/assessments/from-map`
- ปุ่มและสถานะการทำงานบนหน้า Cesium
