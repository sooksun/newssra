# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Thai-language self-assessment web app for screening schools in special/remote areas (สถานศึกษาพื้นที่ลักษณะพิเศษ) to qualify for the พ.ส.ศ. allowance (2,000 THB/month). Schools enter raw facts; the app converts them to scores across 5 dimensions weighted 30/10/30/20/10 = 100 points. Total ≥ 70 → "ระดับ 3 ยุ่งยากมากที่สุด" = eligible; 60–69 = ระดับ 2 and 50–59 = ระดับ 1 (registered but not paid).

Stack: Next.js 16 (App Router, TypeScript, strict) + MySQL (`mysql2`). Deployed with Docker Compose on an Ubuntu server at `/DATA/AppData/www/newssra` (see `docs/DEPLOY.md`).

**Legacy-data analysis toolchain (`npm run legacy:report`)** — evidence base for the 2569 criteria, read-only against the OLD system's database `ssrainfo_ssra` (the PHPRunner-era app, 16 highland items / 15 island items). `scripts/legacy-db.mjs` resolves credentials from `.env.newssra` (gitignored; template `.env.newssra.example`) and falls back to a local snapshot database (`LEGACY_SNAPSHOT_NAME`, currently `ssra_live`) with a warning if the real host is unreachable — the shared host keeps port 3306 closed to non-whitelisted IPs, so the fallback is the normal path until an IP is added under cPanel → Remote MySQL. Refresh the snapshot from a phpMyAdmin export with `node scripts/import-legacy-dump.mjs "<dump>.sql" --db=ssra_live` (streams out just the ~50 tables the analysis needs, ~67 MB of 419 MB; drops and recreates the target only if it carries the `_snapshot_meta` marker it writes, otherwise demands `--force`). That marker records the dump's generation time and file name, and every report prints it — so no output can silently claim the wrong vintage. `scripts/legacy-score.mjs` is a JS port of the old `ScoreService.php`/`IslandScoreService.php` — pinned by `tests/legacy-score.test.ts` against the two real records the PHP app is verified with (highland `1063020130`/2567 = 68.14, island `1091560035`/2568 = 71.38); **every score in the analysis is recomputed from raw values with this one formula**, because the stored `sum_score` is not comparable across rounds (item 1's formula changed between 2565 and 2566 — 17.8% of records differ). `scripts/legacy-items.mjs` holds the item metadata + the six "base data groups" (geo / access / admin / utility / learner / structure, classified by *who owns the data*, not by topic). `scripts/legacy-measures.mjs` classifies the same items on a second, independent axis — **what kind of value each one measures** (continuous / count / percent / mean / ordinal / binary / multiset, plus Stevens scale, unit, origin, and whether the score is normalised by school size). That axis decides which statistics are legitimate per item (report §5 reports mode + median category for qualitative items and refuses to average option codes), what the validation rules must be, and it surfaces the "collected as X, scored as Y" mismatches — highland is 65% quantitative / 35% qualitative by weight, island is the inverse at 22/78. Outputs: `docs/analysis/legacy-item-stats.json` (machine-readable), `docs/ANALYSIS-เกณฑ์เดิมรายข้อ.md` (Thai report), `docs/analysis/legacy-item-report.html` (standalone presentation page), and `lib/legacy-baseline.ts` (**generated — never hand-edit**; prettier-ignored) which exports the empirical constants so criteria code can cite real distributions instead of copied numbers. `scripts/report-answers-summary.mjs` gives the overall answer distribution for every question on the same population the scores are computed from, and ranks the items by **variance share** — `cov(item score, total) / var(total)`, which decomposes exactly (all items sum to 100%) and answers "how much of the score difference between schools comes from this item". It pairs that with the pass/fail flip rate and D, then derives a keep / fix / move verdict per item. Two readings it deliberately guards against with inline caveats: item 16 tops the ranking at 17.9% but its discrimination is circular (it *is* the previous designation), and item 1 has the highest flip rate (24.3%) only because it carries 30 points — with D=0.04 that number says nothing about discrimination. `scripts/legacy-population.mjs` is the shared population builder so every script analyses the identical 1,481/123 rows. `scripts/report-answers-by-year.mjs` answers a different question from the main report: it counts **every row as filed in each round** (not the deduplicated 1,481-school population) so you can see what schools actually answered per item per year. Read it with the caveat it states: 2565 is the one full census (1,623 rows); 2566/2567/2569 are only schools entering or requesting review (228/61/73 rows, non-random), so those columns describe the applicant pool, not a trend. Two things that fall out of it: the applicant pool drops in elevation every round (median 751 → 500 → 467 → 398 m; 84.9% of the 2569 entrants sit below the 500 m line), and blank fields climb from 1.1% to 18.6% per item — which matters because the legacy formula scores a blank as 0 and never distinguishes "ไม่มี" from "ไม่ได้กรอก". Headline finding driving the 2569 design: items 1/3/5/6 (45 points) hand out ~43.6 points to almost every school with discrimination D < 0.15, so the old instrument really separates schools on ~56 points, and the highest-D items (16, 11, 13, 4) carry only 5 points each.

**Criteria simulator (`npm run legacy:simulate`)** — the piece that turns the analysis into decisions: a candidate 2569 instrument is a **JSON file in `scripts/criteria/`** (screening `gates` + weighted `items`), `scripts/criteria-model.mjs` evaluates it, and `scripts/simulate-criteria.mjs` scores all 1,481 confirmed highland schools with it and reports the distribution, pass counts at every cut, per-item discrimination *of the new instrument*, who gains/loses eligibility versus the old one, Spearman ρ against the old ranking, and **the cut that keeps the same number of schools**. Items reference a fixed, documented set of named variables (`VARIABLES` in `criteria-model.mjs`) derived from the legacy raw columns — deliberately no expression language, so every number traces to a column. Two drafts ship as worked examples (`2569-draft-a.json` = elevation becomes a screening gate; `2569-draft-b.json` = no gate, continuous elevation from 300 m) — both are labelled `status: ร่างเพื่อทดลองคำนวณ`, neither is an approved proposal. `tests/criteria-model.test.ts` pins the scoring primitives and asserts every shipped config validates and totals exactly 100. `scripts/report-criteria-html.mjs` turns the simulation JSON into a standalone presentation page (`docs/analysis/criteria-report.html`, `--focus=<config id>` picks the headline draft) — the shared chart/CSS/tooltip pieces both HTML reports use now live in `scripts/html-charts.mjs`. The simulator also runs an **item health check** against acceptance thresholds derived from what went wrong in the old instrument (weight ≤ 25, full-score share ≤ 60%, zero share ≤ 70%, D ≥ 0.20) and names every item that fails and why — both shipped drafts pass only 5 of 12, and the failures are mostly items whose underlying variable barely varies in the population (91% of schools have no branch campus, 87% no impassable road, 79% no bus service), which no reweighting can fix. `docs/EXPLAINER-ร่างค.md` walks through every change draft C makes, with the old formula, the evidence, the new formula, and worked examples of real schools scored item by item; `scripts/report-explainer-html.mjs` renders the same material as a presentation page (`docs/analysis/draft-explainer.html`). `npm run legacy:explain` regenerates both plus the case data in `docs/analysis/draft-explainer-cases.json` — never hand-write those numbers, and note it also carries the size-bias check (score vs school size correlates 0.06 old / −0.05 new, so neither instrument favours small schools) and the legacy-vs-draft health comparison (5/16 → 5/5). `docs/RECOMMENDATIONS-เกณฑ์2569.md` turns the findings into 11 numbered recommendations with the evidence, the trade-off, and an explicit split between technical calls and policy calls; the one caution worth repeating is that item 16 (ประกาศคลัง) has the highest discrimination (D=0.87) precisely because it *is* the previous designation — weighting it heavily would make the instrument re-certify its own past decisions, so it belongs in cross-validation, not scoring. **Calibration result to carry into any 2569 discussion:** once the ~44 free points are removed, both drafts land near a mean of 40–43, so holding the cut at 70 would drop beneficiaries from 490 to ~100 — the equivalent cut is ≈50. Moving the formula without moving the cut is a silent policy change.

Don't run `npm run build` while a `npm run dev` server is running against the same folder — both write to `.next/` and will corrupt each other's cache (manifests as `Cannot find module './NNN.js'` on next dev requests). Stop the dev server first, or just delete `.next/` and restart dev if this happens.

## Architecture

Data flow: client form state → debounced PUT → server recomputes scores → MySQL. The DB row stores the full `state` JSON (source of truth) plus summary columns (`total_score`, `level_key`, `unit_name`, …) that the server derives on every write for the list page — never write summary columns from client-supplied values.

- `lib/types.ts` — shared types; `INDICATOR_IDS` (15 ids `"1.1"`…`"5.2"`) and `AssessmentState` (unit / responses / evidence / feedback / signed / submitted, plus **optional** `gis?: GisAnalysis` + `scoringVersion?: "v2-gis"` — both absent on v1 rows; see the GIS layer below).
- `lib/criteria.ts` — `DIMENSIONS` + `INDICATORS`: single source of truth for criteria text, max scores, level options, evidence requirements. Indicator `kind` is either `"fields"` (raw inputs) or `"level"` (pick-one options; the selected option **index** is stored as a string in `responses[id].level`). Each `IndicatorDef` also carries a `desc` (plain-language explanation) and, for `"fields"` indicators, a `criteria` string list (the score bands) — these feed the per-indicator hover **"?" info popup** in `DimensionPanel.tsx` (`.info-icon-wrap` → `.info-popup`, shown on hover/focus/focus-within, keyboard-reachable via `tabIndex={0}` + `role="tooltip"`), which shows title + `desc` + the bands (for `"level"` indicators it lists `label = points คะแนน` per option instead) + the evidence requirement, so reviewers don't cross-reference the spec doc while scoring. Hidden in print (`.info-icon-wrap { display:none }` in the `@media print` block).
- `lib/scoring.ts` — pure scoring engine: `scoreIndicator` (the per-indicator switch), `flags` (validation flags), `levelFor`, `canSubmit`, `computeAll`. Used by both the client (instant UI) and the server (authoritative recompute on save/submit) — keep it framework-free. `flags()` also imports `derive32Severity`/`primaryRoute` from `lib/gis.ts` for the GIS flags V11/V12/V14/V19/V20 (all guarded by `if (state.gis)` so v1 rows get the identical legacy flag set); every GIS flag is `info`/`warn` only, so `canSubmit` (which blocks only on `block`) is unchanged.
- `lib/state.ts` — `makeBlankState(year = currentBuddhistYear())`/`sanitizeState`. Every payload entering the server passes through `sanitizeState` (drops unknown keys, coerces types, caps lengths). `sanitizeState` is a **strict allowlist** rebuilt from `makeBlankState`, so any new top-level field is dropped on read/save unless explicitly whitelisted — the `gis`/`scoringVersion` fields are handled by a `sanitizeGis(raw.gis)` clause (delegated to `lib/gis.ts`); `makeBlankState` still emits no `gis` key, so v1 rows round-trip byte-identically.
- **Evidence file uploads:** `EvidenceInfo.files: EvidenceFile[]` (`lib/types.ts`) holds metadata only (id, originalName, mimeType, size, sha256, uploadedAt) — the actual bytes live on the filesystem under `uploads/{assessmentId}/{indicatorId}/{fileId}` (`fileId` is a UUID and doubles as the on-disk filename, so no path ever depends on a user-supplied string). `lib/uploads.ts` (server-only: uses `node:fs`/`node:crypto`) does the disk I/O; `lib/upload-constants.ts` holds the shared allow-list/size-cap constants that both `lib/uploads.ts` and the client-safe `lib/state.ts`/`DimensionPanel.tsx` need, specifically so `lib/state.ts` (imported by the client component `AssessmentForm.tsx`) never pulls in `node:fs`. Upload/view/delete go through their own routes (`app/api/assessments/[id]/evidence/[indicatorId]/route.ts` and `.../[fileId]/route.ts`) instead of the general autosave PUT, since files can't travel through a JSON body — after a successful call, the client folds the returned metadata into `state.evidence[id].files` via the existing generic `onEvidence` patch handler (no new handler type needed). Allowed types: JPEG/PNG/WebP/PDF, 10MB/file, 10 files/indicator — enforced both client-side (`accept`, disabled state) and server-side (the actual gate). Deleting an assessment (`app/api/assessments/[id]/route.ts` DELETE) also calls `deleteAllEvidenceFiles()` so its upload folder doesn't linger on disk. Hidden in print like the rest of `.evidence-box`.
- **GIS analysis layer (v2, "prove remoteness from the map"):** `lib/gis.ts` is a **pure, framework-free** engine (client+server shared, like `lib/scoring.ts`; imports only `lib/types.ts` + `haversineM` from `lib/map/morphology.ts` — must **not** import `lib/scoring.ts`, since scoring imports it). It computes **Road Circuity Ratio** (road ÷ straight), **Travel Time Ratio** (actual ÷ reference at `REFERENCE_SPEED_KMH=60`), **Effective Distance** (road × TTR), average speed, and cumulative **elevation gain/loss** (`elevationGainLoss`, 3 m noise floor); maps each to a 0–4 **severity** via `GIS_BANDS` tables (RCR/avg-speed verbatim from the PRD); builds the informational **Auto GIS Score** (`computeAutoGisScore`, max 45 — shown honestly as "X / maxComputable (จากเต็ม 45)" since border/municipality data doesn't exist yet, so those components stay `null` and aren't counted); and exposes `sanitizeGis` + Thai plain-language explainers. **Scoring v2 works by writing derived values *into* `responses["3.1"/"3.2"/"3.3"]`** (`deriveD3Responses`) so the **existing** `scoreIndicator` switch scores them with zero engine changes — 3.1 from the district-office-or-province-hall route's minutes/km, 3.2 from `derive32Severity` (worst-of RCR/TTR/speed/gain → option index 0–4), 3.3 only if a hospital route was picked (else left manual). **Two write paths, one shared processor:** the map's normal one-button flow posts to **`POST /api/assessments/from-map`** (see the map-to-assessment flow below), while the older **`POST /api/assessments/[id]/gis`** stays for an already-open assessment (`requireAssessmentAccess`, so admin/ssra can use it too). Both delegate payload parsing to **`lib/gis-request.ts#buildGisFromMapRequest`** (framework-free, unit-tested) which copies only raw fields from the client (`destinationType`/`destinationName`/`destLat`/`destLng`/`roadDistanceM`/`durationS`/`elevationGainM`/`elevationLossM`/`selected`/`highestPoint`) and recomputes every ratio server-side — no client ratio, score, community class or timestamp is ever retained. It throws `GisRequestError` with codes `INVALID_CENTER`/`INVALID_GIS` (→400) and `NO_VALID_ROUTE` (→422, only when the caller passes `requireProvinceRoute: true`, which `/from-map` does and `/gis` doesn't). The `/gis` route keeps its own guards (**409 after submit**; drops physically-impossible routes; **409** when a re-centre would move `unit.lat/lng` more than `MAX_ASSESSMENT_RELOCATION_M` = 10 km; fills `center.nearestProvinceName` via `listProvinces`+`resolveSchoolProvince` (the school's **registered** province from `master_school.provinces` first, then the entered province, then nearest-hall fallback — so V11 stops false-firing for border districts); applies `deriveD3Responses` + sets `scoringVersion:"v2-gis"` when `apply:true`). **Elevation contract:** `GisElevationInfo.schoolMarkerElevationM` is the elevation **sampled at the school end of the route profile** — never the area mean (`meanElevationM` is a separate field, alongside `minElevationM`/`maxElevationM`/`reliefM`/`maxSlopePct`/`localMaxElevation1KmM`). `sanitizeGis` still reads the pre-v2 key `schoolElevationM` and emits it as `schoolMarkerElevationM`, so legacy rows keep working, but nothing may write the mean into that field again (`tests/route-elevation-flags.test.ts` guards the CesiumMap source against it). `GisRouteAnalysis.highestPoint`, `GisAnalysis.radiusSummaries` (500/1,000/1,500 m rings) and `GisAnalysis.dataSources` (terrain/routing/buildings + `analyzedAt`) are optional and only attached when validation succeeds, so v1 rows stay key-free. **Informational-only extras** (never part of the official 100): `futureIndicators(gis)` returns the two proposed criteria **F1 Displacement Ratio** (straight ÷ road, severity reusing the RCR bands so they can't drift) and **F2 Travel Time Ratio**, rendered in `GisSummary` under "เกณฑ์เสนอเพิ่ม (อนาคต) — ไม่นับรวมในคะแนน 100". The general autosave PUT (`app/api/assessments/[id]/route.ts`) treats `gis`/`scoringVersion` as **server-owned** — preserved-from-DB like `submitted`/`evidence[].files`, via conditional spread so v1 rows stay key-free. `components/GisSummary.tsx` renders the read-only section **"ข้อมูลประกอบเกณฑ์จากแผนที่ 3 มิติ"** in the assessment form: terrain group (school-marker elevation and route-highest point **shown separately**, the latter with its coordinates — same values the two red flags render on the map), route metric table, radius-ring table, polygon area summary, community class, Auto GIS Score, the F1/F2 future-criteria table, the GIS-vs-current D3 comparison that V19/V20 flag, and the data-source list with `analyzedAt` formatted in Asia/Bangkok. Missing values render **"ไม่มีข้อมูล"** (`valueOrMissing`) — never a substituted stand-in; it shows an invite line when `state.gis` is absent. Hidden-in-print rules keep the tables but drop `.gis-actions`. `lib/demo.ts`'s `severe-remote` profile carries a consistent `gis` blob (total stays 98, no V19/V20).
- **Terrain-signature classifier (`lib/terrain-signature.ts`, "ภูเขาสูงทุรกันดาร vs พื้นราบในหุบเขา vs พื้นราบปกติ"):** a **pure** decision tree that answers the landform question the old instrument could not (its elevation item scored D=0.04 — see the legacy analysis). Design + adversarial review in `docs/superpowers/specs/2026-08-07-terrain-signature-classifier-design.md`. Imports only `lib/settlement.ts` + types — **must not import `lib/gis.ts`** (circular with `sanitizeGis`); the caller passes the primary route + severity components so `primaryRoute`/`derive32Severity` stay the single source of truth. Four rules govern it: **(1) three orthogonal axes** — landform (this tree), access severity 0–4 (`derive32Severity`), settlement density (`settlementClass`) — never merged into one number; **(2) local shape is measured relative to the school**, not as absolute elevation (a 505 m valley floor in Pai is not "highland" just because 500 m is a threshold; a 250 m school in Yala can be mountain terrain); **(3) missing data returns `ruleId:"insufficient"` + the exact missing list** rather than a guess; **(4) every answer carries `evidence[]` + `margins[]`** (each deciding predicate's distance to its threshold, with an uncertainty band per input) and `nearBoundary` when any deciding predicate lands inside its band. Tree order (first match wins): **R-I** island (checked before every other gate) → **R0** density ≥ 750 → **R0b** developed large plain (see below) (the `settlementClass` semi-urban cut; density missing ⇒ the urban gate is *unknown*, not *passed*) → **R1** ALT ≥ 1,000 → **R2** mountain (`barrier && !isEnclosed && (isRidge || isSteep || (ALT≥600 && !flat))`) → **R3** narrow valley (`isEnclosed`) → **R4** wide valley (flat + must descend ≥300 m) → **R4b** plateau (flat + must *climb* ≥300 m but barely descend — the vertical direction of travel is what separates ภูเรือ from a valley floor) → **R5** foothill (prominence ≥100 m, no barrier) → **R6/R6b** flat family → **R7** hills. `isEnclosed`/`isRidge` come from the 8-sector flags (`nHigher`/`nLower` vs `SECTOR_RELIEF_K_M`), and they require **≥7 of 8 sectors readable** — otherwise a barrier case returns insufficient, because narrow-vs-wide valley is exactly what sectors decide. **The `!isEnclosed` guard on all of R2 is load-bearing:** valley walls inflate slope, so without it a school at the bottom of a hollow gets called "ไหล่เขา". **R0b screens out "high but not hard": a developed town on a large high plain.** Elevation alone cannot mean hardship — a prosperous town sitting on a broad plateau is flat in every direction, well-roaded, and close to services, yet a pure elevation cut would file it as ภูเขาสูง. R0b fires only when **six conditions hold simultaneously and every input is known** (any missing value → no screening, never a guess): slope ≤ 5%; **grid relief over the ~2.8 km analysis area < `TS_PLAIN_RELIEF_MAX_M` = 60 m** (a genuinely broad plain, not a small terrace between ridges); ≥7 of 8 sectors readable with at most one higher and one lower sector (flat all around within 1 km); RCR, TTR and average-speed severities all known and ≤1 (**`gain` is deliberately excluded** — climbing *to* a plateau says nothing about daily life *on* it, and a genuinely bad road already shows up in TTR/speed); ring density ≥ 300 (flat ≠ developed — there must be a real settlement); and services **provably close**, ≤45 min **and** ≤40 km on the primary route. That last one is written as a positive proof-of-closeness rather than an "unless it's far" escape on purpose: the negative form silently screened out mid-distance schools (50 min / 60 km) that nobody had decided to exclude. When conditions 1–5 hold but proximity fails or is unknown, the school is **not** screened out — it gets a `reviewFlags` entry so a human decides. The 60 m relief cut is calibrated against real rows in this database: mountain-terrain schools measure 173–378 m, and บ้านโคกงาม (639 m, RCR 1.29, 77 km/h — the closest real case to a "high but easy" school) measures 109 m and additionally fails on slope (7.1%) and proximity (53 min / 69 km), so it is protected three times over. `reviewFlags` also feeds `nearBoundary`, so these cases surface in the UI instead of being decided silently. **Island schools are a hard-separated group.** `R-I` runs before the urban gate and the elevation gate, and `group:"island"` can never become `highland_remote`, `valley_flat`, or `flat_normal` — an island peak at 1,200 m stays an island school, because island hardship is *crossing water* and highland hardship is *climbing*, so pooling them makes cross-group score comparison meaningless. Island evidence is any of: the reviewer's `unit.settingType === "เกาะ"`, the AI 3D-image suggestion `unit.settingSuggestion.settingType === "เกาะ"`, or `hasFerry` on the route — and the result lists which one fired under "หลักฐานพื้นที่เกาะ". **"OSRM found no route" is deliberately NOT island evidence**: a highland school with no road yet produces exactly the same signal, and lumping them would do the opposite of separating the two groups (the null-route case is already caught by the data-sufficiency gate, which returns `insufficient` rather than "พื้นราบปกติ"). Honest limitation recorded in the spec: DEM/OSRM as wired today cannot detect islands automatically — coastal plains and open water both read ~0 m, and a school in the interior of Samui or Ko Chang has no water within the 1 km sector radius — so the reviewer's declaration is the authority and `hasFerry` awaits OSRM `steps=true` plumbing to become a measurable signal. Group resolution is deliberately stricter than the landform label: `highland_remote` additionally requires the urban gate to be *known* **and** ≥2 of the 4 severity components at ≥2 — one component (typically cumulative gain) must never certify hardship on its own, or a paved-road plateau resort area scores as remote. **Slope input:** the tree needs slope *around the school*, so `lib/map/morphology.ts#meanSlopeWithinRadiusPct` computes `Morphology.innerSlopePct` (radius `MORPHOLOGY_INNER_SLOPE_RADIUS_M` = 500 m) and it round-trips as `GisElevationInfo.innerSlopePct`; old rows without it fall back to the whole-grid `meanSlopePct` **with the evidence label saying so** and a widened ±4% uncertainty band, never silently. `terrainSignatureFromGis(gis, ctx)` derives everything from a stored `gis` blob, so `GisSummary` renders the section live with **no new storage, no migration, and v1 rows unaffected**. Also fixed here: `morphologyFromGrid` used `provinceOverride?.avgElev ?? 0`, which made every point above sea level "highland" whenever the province row was missing — `provinceAvgElev` is now `number | null` and `isElevationHigh` is null-aware and exported.

- **เกณฑ์ความยากลำบากของพื้นที่ 5 ระดับ (`lib/terrain-difficulty.ts`):** a **pure** module that collapses the terrain/access/community/forest signals into the stakeholder-facing scale 1–5 (1 พื้นราบชุมชนใหญ่ = ไม่ยากลำบาก … 5 ภูเขาสูงสลับซับซ้อนชุมชนชนบท = ยากลำบากที่สุด). Rules that matter: **(1) "สลับซับซ้อน" is the user's own definition** — more than 5 peaks/valleys differing from the school by more than 50 m within a 1 km radius, counted from the 8-sector flags (highest + lowest per sector, max 16 points) → `TD_RUGGED_MIN_POINTS = 6`; fewer than 8 readable sectors returns `rugged: null` ("ยังตัดสินไม่ได้"), never `false`. **(2) Mountain terrain has three independent proofs — elevation, slope, and ruggedness** — because real rows broke every single-signal version: a school on a small flat terrace inside rugged mountains (บ้านนาตอน: 220 m, inner slope 5.9%, but 7 peaks/valleys within 1 km) came out as "พื้นที่ราบ ระดับ 1", contradicting its own ruggedness evidence, so `rugged` counts as mountain evidence too; and `slope > 12%` counts because real rows prove the gap: บ้านนาตอน น่าน sits at 220 m with 25.2% slope and 378 m of grid relief, and an elevation-only test called it "พื้นที่ราบ"; the label then states the reason honestly ("พื้นที่ภูเขา (ลาดชันสูง)" vs "พื้นที่ภูเขาสูง") instead of calling a 220 m school "ภูเขาสูง". **(3) Access is counted per dimension, never collapsed into one number** (`TD_ACCESS_CUTS`: circuity ≥1.8 · speed <30 km/h · time ratio ≥2.0 · cumulative gain ≥600 m · distance ≥146 km = the population's real P75 · route-mountain share ≥50%) · **สันเขาจริงที่ข้าม ≥3 ลูก** (`ridgeCrossings.confirmedCount` — ต่างจากค่าอื่นตรงที่**ยังไม่ได้ calibrate กับประชากรจริง** — ที่มีคือหลักฐานสองโรงเรียนจริง: บ้านพญาไพร 6 ลูก เทียบบ้านโคกงาม 2 ลูก ทั้งที่โคกงามไต่สะสม 835 ม. ผ่านเกณฑ์ gain — มิตินี้จึงบอกสิ่งที่ gain บอกไม่ได้ คือ "ไต่ยาวลูกเดียว" กับ "ขึ้นลงหลายรอบ"; แถวเก่าที่ไม่มีค่า → `null` ไม่นับทั้งเข้าและออก และขึ้นใน `missing`) — ≥3 dimensions = "เข้าถึงยากหลายด้าน", which is what separates level 3 from level 4. **(4) Forest support requires the real forest-cover layer, never the legal reserve boundary** — the adapter reads the saved layer's `authority` into `forestSource: "cover" | "legal" | null`, and anything but `"cover"` gives no support, because "inside a declared reserve" and "still forest today" are different questions (a reserve polygon that became a village must not earn hardship points); rows saved before the cover layer existed report "มีแต่แนวเขตป่าสงวน — บันทึกจากแผนที่อีกครั้ง" in `missing`, and the evidence line always names the source. Measured on บ้านพญาไพร: the cover layer gives inside=1 / 100% at 1 km → level 4 with support, while the legal layer gives inside=0 / 0% at 1 km → level 3 without — same school, opposite answers. Forest is still only a supporting signal, never a gate: it lifts the level by **at most one step**, only for a highland rural school inside forest with ≥60% at 1 km or ≥50% at 3 km, and **never past level 4**: level 5 must come from measured terrain ruggedness, per the forest spec's rule that the legal layer alone must not decide scoring. Missing school-marker elevation or community size → `level: null`, since both appear in the definition of every level. **`GisRouteAnalysis.ridgeCrossings`** (`lib/map/routeWaves.ts` — pure, **ห้าม import `lib/gis.ts`**) นับ "กว่าจะถึงโรงเรียนต้องข้ามภูเขากี่ลูก" — สุ่มความสูงทุก 50 ม. บน **3 แนวขนาน** (กลางถนน + ซ้าย/ขวา ±200 ม. คงที่ ไม่สุ่ม) แล้วนับด้วย hysteresis: ไต่จากหุบ ≥50 ม. **และ**ลงจากยอด ≥50 ม. = 1 ลูก (ไต่ท้ายเส้นโดยไม่ลงก็นับ — คือเขาที่โรงเรียนตั้งอยู่). **แนวข้างคือหัวใจของมัน**: ยอดแนวกลางที่มียอดแนวซ้ายหรือขวาภายใน ±300 ม. ตามแนวเส้น = `confirmed` ซึ่งแยก "ข้ามสันเขาจริง" ออกจาก "ถนนเลียบหุบ/เจาะช่องเขา" ที่โปรไฟล์กลางหลอกว่าแบน — เกณฑ์ 5 ระดับใช้ `confirmedCount` เท่านั้น. นับฝั่ง client (server ไม่มี DEM จึง validate ช่วงค่าอย่างเดียวด้วย `cleanRidgeCrossings` — ข้อจำกัดเดียวกับ `elevationGainM`), deterministic ทั้งหมด (ห้าม `Math.random()`) เขียนเฉพาะเมื่อมีค่า แถว v1 จึง round-trip เหมือนเดิม. สเปก: `docs/superpowers/specs/2026-08-08-route-ridge-crossings-design.md`. **`GisRouteAnalysis.mountainPct`** (the share of route samples at ≥500 m, from `routeMountainPercent` in `lib/map/routeElevation.ts`) is a new stored field answering "how much of the access route is mountain terrain" — distinct from the single highest point and from cumulative gain; it is written only when present, so v1 rows still round-trip byte-identically.

## Domain Rules (from the spec — do not violate when touching scoring)

The authoritative spec is `docs/ข้อเสนอเกณฑ์และตัวชี้วัด-พสศ-v1.md`: per-indicator scoring tables in §4 (use the "เสนอ" column), cut-off logic in §5, roles/data model/workflow for the intended full system in §8, validation flags V01–V10 in §8.5. Implemented flags: V02, V04, V06, V07, V09 + app-local V00 (count > total students) + the GIS-only set V03 (manually-entered 3.1/3.3 travel time > 50% above the GIS route's `travelTimeMin`), V11 (pin nearest a different province hall than `unit.province`), V12 (road < straight distance), V14 (RCR > 3), V19/V20 (GIS-derived vs. manually-picked 3.2 severity differ by ≥2) — the GIS flags fire only when `state.gis` exists and are `info`/`warn`, never `block`. Tone `"block"` prevents submission. **Deliberately NOT implemented (need a data source the app doesn't collect):** V01 (deviation from a central enrollment DB — no central reference), V05 (photo GPS > 5 km from school — evidence files store no EXIF/GPS), V08 (dimension-5 answer vs a central registry — no such registry), V10 (uploaded file "looks like a personal name list" — needs content classification, only magic-byte sniffing exists). Don't fake these — they require the missing data before they can fire faithfully.

- Users enter raw data only (counts, minutes, level selections) — never add an input where a user types a score directly, and never trust client-computed scores (server recomputes via `lib/scoring.ts`).
- Normal conditions = 0 points; no free base points anywhere.
- Score ranges follow "เกิน a – ไม่เกิน b" (exclusive lower bound, inclusive upper), with no gaps or overlaps; percentages use 2 decimal places.
- PDPA: student data is aggregate totals only — the app must never collect or accept individual student name lists (ethnicity, poverty, disability, and registration status are sensitive data). Keep everything utf8mb4.
- **Authentication + 3 roles are implemented, with hybrid login.** `admin` (see/edit all + user management), `ssra_admin` (see/edit all), `school` (see/edit only their own school's assessments). No new deps: `lib/auth.ts` (server-only) does scrypt hashing + an HMAC-signed httpOnly session cookie via `node:crypto`; `lib/auth-constants.ts` holds the edge-safe cookie-name constant so `proxy.ts` (Next 16's renamed middleware convention — redirects unauthenticated page requests to `/login`) never imports `node:crypto`. **Two account sources (login tries them in order):** (1) `lib/users-repo.ts` `users` table — local admin/ssra_admin accounts (scrypt-hashed), seeded on first DB connect via `seedDefaultUsers` (only `admin`+`ssra_admin`; **schools are NOT seeded here**); (2) `lib/legacy-users-repo.ts` reads the pre-existing legacy `` `user` `` table (~3,158 real school logins from the old SSRA system, keyed by an 8-digit `user` code, **plaintext passwords 5–6 chars** — compared directly; note the security caveat). A legacy match becomes a `school` session with `schoolCode` = the 8-digit code, and triggers **lazy migration** (see the migration note below): a scrypt-hashed row is written to the `users` table so subsequent logins use the hashed path, not the plaintext one. **Session** (`SessionUser`) carries `{uid, role, name, source: "local"|"legacy", schoolCode}`. **School scoping is by school code:** assessments carry `owner_school_code` (+ `owner_user_id`), `lib/repo.ts#listAssessments(viewer)` filters `school` viewers by `owner_school_code = viewer.schoolCode`, and `canAccessAssessment(user, ownerSchoolCode)` gates single rows (empty schoolCode ⇒ sees nothing; `null !== ""` guards blank owners). Local `users` rows can also hold a `school_code` (set via the admin UI). **Admin user management** (admin-only) lives at `app/admin/users/page.tsx` (`requireRole("admin")`) + client `components/UsersAdmin.tsx`, backed by `app/api/admin/users/route.ts` (GET list / POST create — username must match `^[a-zA-Z0-9_.-]{3,64}$`, password ≥6 chars, duplicate username → 409) and `app/api/admin/users/[id]/route.ts` (PATCH `role`/`displayName`/`active`/`password`/`schoolCode`). A `countAdmins(true) <= 1` guard blocks demoting or deactivating the **last active admin** (so you can't lock yourself out); there is no hard-delete — accounts are just deactivated (`active=false`). This UI manages **local `users`** — including school accounts that have been **migrated** from legacy on their first successful login (once migrated they appear here and an admin can reset the password / deactivate them); un-migrated legacy 8-digit logins don't appear until their first login. `components/UserMenu.tsx` is the top-right name/role dropdown with logout (POST `/api/auth/logout`), hidden in print. Columns are migrated in `lib/db.ts#init()` via `information_schema` checks (MySQL 8 lacks `ADD COLUMN IF NOT EXISTS`). **Guard pattern:** pages use `requireUser()`/`requireRole(...)` from `lib/auth.ts`; API routes use `requireApiUser()`/`requireApiRole(...)`/`requireAssessmentAccess(id)` from `lib/api-auth.ts` (returns `{ok,response}` — return `guard.response` on failure). The legacy `` `user` `` table is **read-only** to this app (never written/altered; `user` is a MySQL reserved word so always backtick it). `AUTH_SECRET` (env) signs sessions — dev falls back to a default **with a warning**, but **production throws (fail-closed) via `authSecret()` if it's missing, `<16` chars, or equal to the dev default** (every request touching a session fails until it's set). Seed passwords behave similarly: dev defaults to `admin123`/`ssra123`, but production **auto-generates a strong random password and logs it once** when `SEED_ADMIN_PASSWORD`/`SEED_SSRA_PASSWORD` are unset (no known-weak default on prod). **Login is rate-limited** (`lib/rate-limit.ts` — in-memory fixed-window `RateLimiter`, 10 fails / 15 min → 15-min block, checked per-IP *and* per-username; returns 429 + `Retry-After`; IP taken from `x-forwarded-for`/`x-real-ip`, skipped when unresolvable so one shared key can't lock everyone out; success clears the counters). **Legacy plaintext passwords migrate to scrypt lazily on successful login** — a hashed `users` row is created (the read-only `` `user` `` table is never written), with a **self-healing rehash** path for `school` accounts if the legacy password later changes; full rationale + phases in `docs/AUTH-MIGRATION.md`. Trade-offs: stateless cookie ⇒ deactivation takes effect next login (7-day expiry); rate-limit state is in-process (resets on restart, not shared across instances — swap for a shared store if scaling out).

## Deployment

`Dockerfile` (multi-stage, standalone output) + `docker-compose.yml` (app on host port 9950 → container :3000 + MySQL 8.4 with data bind-mounted at `./data/mysql`, uploaded evidence files at `./data/uploads` → container `/app/uploads`). Both services read `.env.production`. Full runbook in `docs/DEPLOY.md`, including the variant that points at an existing host MySQL via `host.docker.internal`.

**Run `npm run db:init` against the target database before cutting over.** The `uq_owner_school_year` migration is fail-closed: if the existing data already holds more than one assessment for the same school and year, `init()` throws on every request (the app, including the admin UI, stays down) until the duplicates are merged or deleted by hand. Running `db:init` first surfaces the exact `school / year / ids` groups while the old version is still serving.

UI text and domain terminology are Thai — keep wording consistent with the spec when adding features.
